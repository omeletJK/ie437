# IE437 과제 1 수업 사례 검토

검토일: 2026-10-11. 수업 시작 파일은 [index.html](index.html)이다. 영어 발표본 두 개와 독립 실행 데모 두 개를 연결해 두었다. 공개 수업 사이트나 과제 배포 ZIP은 수정하지 않았다.

두 자료는 **해결 전략을 비교하는 좋은 참고 사례**다. 원래의 제안서만을 완성된 과제 모범 답안으로 제시하면 문제 정의·데이터 해석·구현 증거의 빈틈이 생긴다. 수업에서는 새 문제 정의 해설과 데모의 실제/예시 표시를 함께 사용한다. 특정 모델이 유일한 정답이라는 메시지도 피한다.

## 확인한 과제

- 현재 과제는 `ie437-slides/teaching/assignment-01-movie-programming/student/assignment.md` v2.1이다. 제출 마감은 2026-10-09 23:59 KST로 명시되어 있다.
- 영어 문제 정의서, 인터랙티브 데모, 제안 발표의 세 파일이 일치해야 한다. 문제 정의서는 7개 항목, 두 접근 비교, 학생 본인의 중요한 LLM 검토 3건을 요구한다.
- 공개 기본 배점은 문제 정의 50, 데모 25, 발표 25다. 특정 알고리즘을 요구하지 않으며 정당화한 단순 해법으로도 높은 점수를 받을 수 있다.
- 데모는 동일 조건의 기준안 비교, 입력 변경과 재실행, 정상·경계·실패 사례, 재현성과 오프라인 실행을 요구한다. 정적 화면이나 이유 없는 숫자 변경만으로는 충분하지 않다.

확인 범위에서 **실제 학생 제출 답안은 발견하지 못했다.** 두 로컬 프로젝트에 제출 파일이 없었고, 원본을 변경하지 않고 복사한 로컬 플랫폼 DB의 제출/파일/수정 이력 수는 모두 0이었다. 그 DB의 과제는 이전 토이 과제다. 다른 LMS나 운영 서버에 제출된 학생 답안의 존재·내용·제출 여부는 이 결과로 판단할 수 없다. 이번 적합성 검토는 배포된 과제 설명과 평가 기준에 대한 검토다.

## 두 사례의 적합성과 한계

| 관점 | Response Model 사례 | Synthetic Audience 사례 |
|---|---|---|
| 핵심 통찰 | 편성이 반응과 실현 수요를 바꾸므로 고정 수요 배분만으로 충분하지 않을 수 있다 | 관측과 양립하는 가상 관객의 선택을 모사하고 합산할 수 있다 |
| 실제 실행 | S13의 합성 반응 수식 평가와 결정론적 ILS 탐색 | S09A의 seed 기반 일별 선택 추첨·이력 갱신 |
| 예시와 구분 | 반응 버튼의 준비된 값과 토이 평가식을 실제 학습/인과 효과로 부르지 않는다 | S22 A/B와 S23의 6개 점수·편성 변경은 준비된 설명 값이다. S23의 누적 관객 실행 수가 실제 엔진 호출 수라고 설명하면 안 된다 |
| BO | 실제 BO 구현은 없다. ILS를 정확히 명명한다 | 실제 BO 구현은 없다. 평가 모델과 탐색 알고리즘을 구분한다 |
| 주요 보완 | 변수·단위·목표·제약·가정, 평가 Component Role/Model, 관측 편향과 검증 조건 | 구매자와 관객의 차이, 가상 집단 구성과 선호의 식별 한계, 복수 가정·시장 보정·민감도 |

`account_tag`가 구매자이고 `passes_bought`가 티켓 수라는 사실이 중요하다. 구매자 이력을 동반자 전원의 이력으로 복제할 수 없으며, 티켓 수·고유 관객·실제 입장·개인 선호는 서로 다른 목표다. 상영 날짜와 시각만으로 구매 시점의 정보 가용성을 알 수도 없다. 미판매 회차, 용량, 전체 편성, 변경 이력, 운영 제약을 요청해야 한다.

참고 데모는 원래의 예시 관객·방문 점수를 유지하며, HW1 해설의 구매 티켓 수 목표를 구현하거나 검증한 것이 아니다.

분류는 경계에서 도출한다. 한 번 정한 전체 편성은 Flat/Stateless/Open-loop로 정의할 수 있다. 시뮬레이터 내부 기억이나 모델 파이프라인의 순서만으로 편성 문제가 Stateful/Feedback/Hierarchical이 되지는 않는다. 새 관측과 확정 예약이 이후 결정에 영향을 주는 재편성은 별도 상태·전이·정보 구조로 정의한다.

## 수업 진행

1. 런처의 6개 필드와 관측 단위를 먼저 보인다. 무엇이 알려졌고 무엇이 가정인지 학생에게 묻는다.
2. Response 데모의 Response controls → Search를 연다. 같은 조건의 기준 5,134와 탐색 5,265, 0 위반, 계산 호출을 확인한다. 이 숫자는 토이 목적함수 결과이며 사업 성과가 아니다.
3. Audience 데모의 Daily sampling을 실행·재설정한다. 단일 결합분포, 관람 이력, 재현 가능한 난수 경로를 설명한다. A/B·Search storyboard는 준비된 설명 값이라는 표시를 함께 읽는다.
4. 두 데모의 HW1 case checks를 연다. 2개 스크린 × 3개 고정 슬롯에서 요구 회차 4/6/7을 실행한다. 이는 추가한 투명한 제약 계산 예이며 전체 엔진의 검증을 대신하지 않는다.
5. 평가 모델과 탐색 알고리즘을 분리한다. 반응 모델 또는 합성 소비자 모델을 선택한 뒤에도 enumeration/ILS/BO 선택은 별개다. 네 후보를 싸게 평가할 수 있으면 전수 비교로 충분하다.
6. 공통 기준안·정보 cutoff·목표 단위·평가 조건을 정하고, 실제 데이터에서 확인할 사항과 진행/수정/중단 기준으로 마무리한다.

발표 전체보다 핵심 슬라이드를 골라 쓴다. Response는 S01/S02/S05/S06/S07/S09/S11/S12/S13/S14/S19/S36, Audience는 S01/S02/S06/S09/S09A/S14/S17A/S18/S19/S22/S28/S37을 권장한다. 키 S는 기본 발표 경로/전체 모드를 전환한다. 데모의 상단 선택 메뉴는 필요한 화면으로 직접 이동한다.
